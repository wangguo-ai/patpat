# Codex介绍

> Codex 是 OpenAI 面向软件开发工作的 AI 编码代理。本文用于在本仓库中快速说明 Codex 的定位、能力边界和推荐使用方式。最后更新：2026-06-30

---

## 一句话定位

Codex 可以理解为一个会读仓库、会改代码、会跑命令、会检查结果的 AI 开发搭档。

它不只是聊天助手，而是更接近“带工具的工程执行者”：可以根据任务目标阅读文件、理解现有结构、修改文档或代码、运行测试/脚本，并把结果反馈给用户。

---

## Codex 能做什么

### 代码与文档工作

- 阅读仓库文件，理解项目结构和已有约定。
- 新增、修改、重构代码或 Markdown 文档。
- 查找 bug、解释代码、做代码审查。
- 根据已有风格补充 README、技术方案、操作手册、决策表等资料。

### 本地执行与验证

- 在当前工作区运行命令、脚本、测试和格式化工具。
- 检查 Git 状态，避免覆盖用户已有改动。
- 对前端页面、自动化脚本、数据处理流程做运行验证。
- 在需要联网、写出工作区或执行高风险操作时请求用户确认。

### 工具与外部系统

- 通过技能、插件和 MCP 连接更多能力，例如浏览器自动化、飞书、Obsidian、图片生成、文档转换等。
- 在合适场景下使用专门技能，而不是每次从零写流程。
- 把重复性工作沉淀成文档、脚本、技能或自动化任务。

## Codex 适合本仓库的场景

### 知识库维护

- 补充业务流程、系统说明、Agent 角色说明。
- 整理散落的操作经验，形成稳定的 Markdown 笔记。
- 检查笔记之间的 Obsidian 链接是否清晰。

### 自动化开发

- 编写和维护 Python、Playwright、RPA 辅助脚本。
- 梳理图灵 ERP、报销上传、供应商凭证、采购入库等流程的自动化步骤。
- 把临时脚本升级为可复用工具，并补充输入输出说明。

### 多 Agent 协作

- 明确阿文、小王、小吴、小李等 Agent 的职责边界。
- 把执行顺序、异常处理、凭证匹配规则写成可检索的知识库内容。
- 将一次性任务复盘为可复用的操作指南。

## 使用 Codex 的推荐方式

### 1. 先说目标，再说约束

好的指令示例：

```text
帮我新增一篇介绍 Codex 的文档，放在技术目录，风格和现有知识库一致，不要修改其他文件。
```

比起只说“写个文档”，明确位置、用途、风格和边界，会让 Codex 更容易一次做到位。

### 2. 把长期规则写进仓库

适合长期保留的内容：

- 仓库结构说明。
- 常用命令和验证方式。
- 文件命名规则。
- 自动化任务的输入输出模板。
- Agent 读取顺序和禁止行为。

这些内容应该放进知识库或项目配置中，而不是只留在一次聊天里。

### 3. 让 Codex 自己检查结果

对代码任务，可以要求：

- 运行测试。
- 检查格式。
- 给出改动文件清单。
- 说明无法验证的部分。

对文档任务，可以要求：

- 检查链接。
- 保持和现有文档风格一致。
- 不改动无关文件。

## 能力边界

Codex 很适合处理结构化、可验证的开发和知识管理任务，但仍需要注意边界：

- 对外部平台的最新状态，最好联网或调用对应工具确认。
- 对涉及付款、审批、删除、覆盖、批量改名等高风险动作，应先确认再执行。
- 对业务事实，应该以仓库内规则、表格、系统记录和用户确认作为最终依据。
- 对临时判断，应该在结果中说明依据和不确定性。

---

## 在本仓库中的协作原则

1. 先读相关知识库，再执行任务。
2. 优先复用已有脚本、规则和命名方式。
3. 不覆盖用户未要求修改的内容。
4. 把一次性经验沉淀成可复用文档。
5. 自动化结果要能追溯：输入、处理逻辑、输出位置都要写清楚。
